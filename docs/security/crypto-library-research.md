# Cryptographic Library Research for OmniCloud E2EE

**Status:** Research note; not a library selection, protocol specification, or security approval. A temporary, isolated prototype was run outside the repository; no package was added to the project and no production implementation was tested.

**Date:** 2026-10-17

**Related:** [`architecture-decisions/0001-e2ee-platform-and-library-evaluation.md`](architecture-decisions/0001-e2ee-platform-and-library-evaluation.md), [`encryption-protocol-proposal.md`](encryption-protocol-proposal.md).

## Executive recommendation

Prototype **libsodium `crypto_secretstream_xchacha20poly1305` via libsodium.js** first for the chunked content-encryption path because its documented purpose directly covers authenticated message streams/files: it authenticates sequence order and detects truncation/removal/reordering/duplication/modification, manages stream nonces, and uses an explicit final tag. The JavaScript wrapper documents browser and Node use.

This is a **candidate for evaluation, not an approved choice**. The format is libsodium-specific. Android would need an interoperable libsodium implementation/binding, not a different AEAD with a similar name. The pinned JS wrapper exposes opaque state handles but no published release provides a supported way to release them: `free()` is implemented in upstream master (added 2026-05-20, hardened 2026-05-23/24) yet the latest npm release, 0.8.4 (2026-04-19), predates it. Do not reach into internal WASM exports to dispose of state. Until a release containing the supported `free()` API is available (or another binding provides equivalent lifecycle control), long-lived secretstream use in this wrapper is a candidate-selection blocker. The test-only Web/Node exchange passed after converting bytes with wrapper helpers. The library's documentation does not substitute for reviewing the exact version, wrapper, bindings, build artifacts, or protocol design.

If the project requires native Android Tink/Keystore and standardized Web Crypto/Node primitives without a compatible libsodium implementation, the alternative is a reviewed common chunk protocol built over a common AEAD. That option leaves more security-critical framing, finalization and nonce logic to OmniCloud and should not be selected just for primitive/API popularity.

**Do not use Web Crypto AES-GCM as though it were a complete streaming file format.** It supplies low-level cryptographic operations, not the file protocol, authenticated manifest, resumability rules, or cross-platform envelope.

## Candidate-specific notes

### libsodium secretstream: evaluate first for content stream

The secretstream documentation establishes properties that map closely to OmniCloud’s chunking requirements: per-message authentication; hidden message tags; stream header; internally managed nonce and rekeying; `TAG_FINAL`; and detection of sequence corruption. It does not decide how OmniCloud binds a stream to account/file/version/key epoch. Define such authenticated context explicitly during the protocol review.

Prototype requirements:

- Verify whether the chosen JS wrapper exposes every needed secretstream operation and parameter consistently in browser and Node.
- Use a pinned package version and record the exact source/release/provenance; review wrapper generation and WASM/native build artifact supply chain.
- Require `TAG_FINAL`, reject bytes after finalization, reject EOF before finalization, and do not publish partial plaintext as verified. Confirm behavior for empty files and partial final chunks.
- Release encrypted stream state in all success and error paths. For the JS wrapper this requires a published release containing upstream `free()` (master only as of 2026-10-17); verify that freed memory is zeroed and that use-after-free/double-free are rejected before relying on it.
- Test browser worker and stream integration, memory copies, cleanup, performance, bundle weight and supported browsers.
- Evaluate Lazysodium Android as one possible binding: upstream describes Kotlin compatibility, and its v5.2.0 release notes state libsodium 1.0.20 support and recommend minimum API 24. Test the exact `secretstream` calls, byte serialization, supported ABIs, native artifacts and build provenance. Do not assume Android API calls serialize identically merely because the primitive has the same name.
- Confirm whether API 24 as the minimum is acceptable for the product; otherwise identify and verify a maintained alternative rather than silently lowering the SDK requirement.

### `@noble/ciphers`: candidate for primitive-based multi-platform JS

The documentation reports an independent Cure53 audit of version 1.0.0 (September 2024), but current version and audit applicability must be confirmed before selection. It exposes AEAD and key-wrap APIs, but describes byte-array message operations, not an authenticated streaming file format. If selected for content encryption, OmniCloud would own protocol-critical chunk framing, nonce lifecycle, finalization, ordering and resume semantics. Its docs themselves explain nonce uniqueness and advise against random 96-bit nonces for large message counts; adhere to the chosen algorithm’s documented limits and get the protocol reviewed.

Potential benefit is readable JavaScript, multi-runtime support and audited historical version. Limitations include JS timing/GC caveats, no turnkey secretstream format, separate Android implementation, and potentially separate library/version choices for native Android.

### Standard APIs: interoperability is not automatic

Web Crypto and Node crypto can provide familiar primitives; Android APIs/libraries can provide related primitives. The resulting ciphertexts are not automatically interoperable because applications must agree on key representation, algorithm parameters, serialization, nonce rules, AAD bytes, tag handling, key wrapping, chunk framing and finalization. Choosing “AES-GCM everywhere” is not a protocol decision and does not resolve those requirements.

## Proposed evaluation sequence

1. **First prototype:** libsodium.js secretstream in Web and Node (not connected to account/API/storage), with test-only fixed vectors and random-key tests. Measure bundle and stream performance.
2. **Android feasibility:** evaluate Lazysodium Android (currently documented v5.2.0 / libsodium 1.0.20 / recommended minimum API 24) as a candidate, build a tiny vector runner, inspect native artifact provenance and assess Keystore integration for local wrapping-key storage. Separately compare native Tink + common-format alternative if minimum SDK, compatibility or supply chain is unacceptable.
3. **Alternative prototype:** compare `@noble/ciphers`/WebCrypto AEAD operations and Android implementation only as a protocol-construction exercise; quantify the extra framing/nonce/finalization machinery OmniCloud must specify and review.
4. **Security/design review:** present exact library versions, APIs, format proposal, nonce and resume logic, test vectors, dependency/provenance evidence and limitations to an independent cryptographic reviewer.
5. **Decision record:** only after those steps, choose and pin a construction/library/format or reject all candidates. Do not update release docs or add production dependencies before acceptance.

## Questions still open

- Is the measured test-bundle weight acceptable? The isolated prototype bundle was 483,431 bytes raw / 154,549 bytes gzip without minification; re-measure a minified, tree-shaken, production-integrated build before judging web cost. (Upstream README's ~290 KB standard / ~375 KB sumo estimate is from the wrapper project and not directly comparable.)
- Must selection wait for an upstream libsodium.js release containing `free()` for state release, and if so how long is acceptable, or should another binding be evaluated in parallel?
- Is a trustworthy Android libsodium binding available for the selected Android minimum version, and can its build provenance be reviewed?
- Should the protocol embrace libsodium secretstream's format to reduce custom stream logic, or prefer a common primitive with a separately specified stream format to ease native API support?
- How will resumable uploads preserve the secretstream state safely across process restarts? Persisting stream state or restarting with a new DEK/stream has distinct security, idempotency and storage costs.
- What authenticated context binds the server object/file/version IDs when IDs may be allocated during upload?
- What visible metadata and search capabilities are accepted?

## Isolated prototype results

A temporary prototype was created under `/tmp/omnicloud-e2ee-prototype` and removed after testing. It used a test-only 4-byte length prefix per secretstream record and a header at the start; this framing is not a production format. No OmniCloud source, manifest, lockfile, API, database, account or user data was used.

- **Pinned packages:** `libsodium-wrappers@0.8.4` and transitive `libsodium@0.8.4`, both ISC. npm reported integrity values `sha512-mu8aAWucZjTB5O/BtGXtW4e1agy7uHxNYG7zPthmmD1jU43LCDmSWZLN4JhflbdPXj3yDO4lxM1O9hLDgIOXDw==` and `sha512-lMcYaRi0zcs7tarATsQUYC7rstliIXZuoq0c6zXSgNtSNtdvBgkSegjWhpMJAXzKX3SUSwIp7+zEsob+j3LuRw==`, respectively.
- **Runtime exchange:** Node 24.21.0 ↔ Firefox 157.0.1 (headless Linux), both directions, 150,123 deterministic synthetic bytes split into three 64 KiB-ish records. Both decryptions matched the source bytes.
- **Negative tests in Node:** wrong key, mutated final ciphertext, removed final record, reordered records, duplicated record, record after final, truncated length prefix, undersized record, and modified header were rejected. Firefox rejected a mutated final ciphertext; the wrapper surfaced this test as “missing final tag” because the prototype did not distinguish authentication failure from lack of a valid final record. Production behavior must treat either as a hard failure and discard partial plaintext.
- **Other Node round-trips:** empty, 17 bytes, 65,559 bytes and 8 MiB fixtures passed; the empty file was represented by one authenticated final record.
- **Bundle:** esbuild IIFE browser bundle measured 483,431 bytes raw / 154,549 bytes gzip. This was not minified, and excludes OmniCloud-specific integration; compare only as a prototype baseline.
- **32 MiB timing/memory sample:** Node 24.21.0, three repeated encrypt/decrypt runs. Encrypt took 331–523 ms; decrypt took 411–583 ms. RSS rose from approximately 124 MB baseline to 262–328 MB across the repeated runs. This harness buffers full plaintext/ciphertext and retains allocations; these numbers are noisy and are not a library-only benchmark or evidence of streaming memory performance.
- **State lifecycle blocker (now explained):** `libsodium-wrappers@0.8.4` returns a numeric secretstream state handle and exposes no supported release function. Upstream master added `free()` on 2026-05-20 (state tracking and heap zeroing hardened 2026-05-23/24) with tests for invalid/double/untracked free and zeroed memory, but the latest npm release 0.8.4 was published 2026-04-19 and its tag contains neither `free()` in `wrapper/wrap-template.js` nor any mention in its README. So this is an unreleased upstream feature, not a broken export in the published package. Consequences: (a) repeated streams in one process leak WASM heap allocations, and (b) released stream state is not zeroed, so key material can linger in the WASM heap. The prototype used short-lived processes accordingly. Do not call `_free` or other undocumented WASM exports directly. Gate JS-wrapper selection on a released `free()` (or equivalent verified lifecycle control from another binding).
- **Android:** not tested. Gradle and `adb` were unavailable; no Android SDK/toolchain was installed. Lazysodium Android compatibility, ABI/native provenance and minimum API remain unverified.

### Interpretation

The prototype establishes **basic JS/Web ↔ Node secretstream API compatibility for the tested package/runtime pair**, not a secure OmniCloud protocol. It does not evaluate DEK wrapping, AAD/context binding, manifest semantics beyond the library final tag, resume after process restart, state cleanup, actual streaming/backpressure, file writes, plaintext staging, Android interoperability, or independent security. The package must not be selected solely on this result.

## Limitations

This is a documentation-based comparison plus a narrow temporary interoperability experiment, not a production code review, full streaming benchmark, vulnerability assessment, or independent cryptographic review. Upstream statements about audits, platforms, bundle size and maintenance are attributed to those sources and require verification for the exact versions selected. No library is endorsed for production by this document.
