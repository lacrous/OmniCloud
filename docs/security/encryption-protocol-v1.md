# OmniCloud E2EE Protocol v1 (OCE1) — Concrete Specification

**Status:** Implemented provisionally in `packages/crypto` and integrated into the API, SDK, and Web client as an **opt-in experimental** feature. This specification and implementation **require independent cryptographic review before any production or user-facing enablement**. Not reviewed; do not describe OCE1 as audited or production-ready.

**Stack decision:** see [`architecture-decisions/0002-e2ee-crypto-stack.md`](architecture-decisions/0002-e2ee-crypto-stack.md). Primitives: XChaCha20-Poly1305 AEAD and HKDF-SHA256 from `@noble/ciphers@1.3.0` / `@noble/hashes@1.8.0`. These are established primitives from maintained libraries; the OmniCloud-specific framing below is new and is the part that needs review.

**Supersedes for implementation purposes:** the open algorithm questions in [`encryption-protocol-proposal.md`](encryption-protocol-proposal.md) (that document remains the architectural proposal). The libsodium secretstream option was dropped for v1 because no published `libsodium.js` release provides supported stream-state release ([`crypto-library-research.md`](crypto-library-research.md)).

## 1. Goals and non-goals

Goals for OCE1:

- Client-side authenticated encryption of file content before upload; API/Telegram handle opaque bytes only.
- Independent random data key (DEK) per file version; user root key (URK) never leaves the client.
- Authenticated chunk ordering and completion; detect tamper, truncation, reorder, duplication, wrong key, unsupported versions.
- Streaming-friendly processing with bounded per-chunk memory.
- Encrypted filename/MIME/description metadata.
- Legacy plaintext files remain supported and explicitly distinguished.

Non-goals (deferred to later reviewed phases): multi-device enrollment protocol, recovery code format, server-side encrypted search, sharing, Android implementation, rollback/freshness protection against a malicious server, key-epoch rotation UX.

## 2. Keys

- **URK**: 32 random bytes, generated by the client (`generateUrk`), held only by trusted clients. Never sent to API/Telegram.
- **KEK** (data-key wrapping): `HKDF-SHA256(ikm=URK, salt="omnicloud-e2ee-v1", info="omnicloud/e2ee/v1/dek-wrap", length=32)`.
- **MEK** (metadata): `HKDF-SHA256(ikm=URK, salt="omnicloud-e2ee-v1", info="omnicloud/e2ee/v1/metadata", length=32)`.
- **DEK**: 32 random bytes per file version (`generateDek`). Encrypts that version's content records.
- **Recovery key** (optional record): `HKDF-SHA256(ikm=recoveryCode32, salt="omnicloud-e2ee-v1", info="omnicloud/e2ee/v1/recovery", length=32)`. Wraps the URK into the fixed 72-byte recovery record the server stores but cannot open; format and limits are normative in [`recovery-and-device-revocation.md`](recovery-and-device-revocation.md).

Domain-separation strings are ASCII, part of this specification, and covered by tests/vectors.

## 3. Identifiers and epoch

- `fileId`: 16 random bytes, client-generated at first encrypted upload of a file.
- `versionId`: 16 random bytes, client-generated for every new encrypted version.
- `keyEpoch`: `uint32` big-endian, `0` in v1. Reserved for future URK rotation; clients MUST reject epochs they cannot unwrap.

Server-side identifiers (Postgres/Telegram) are unrelated to these client ids and do not enter the envelope. Binding to the server account is out of band for v1: authorization remains server-side; content authentication binds only to the client ids.

## 4. Envelope bytes (stored object content)

```text
Header (48 bytes):
  offset  size  field
  0       4     magic = 0x4F 0x43 0x45 0x31  ("OCE1")
  4       1     version = 0x01
  5       1     suite = 0x01  (XChaCha20-Poly1305 + HKDF-SHA256)
  6       1     flags = 0x00  (MUST be 0; nonzero = reject)
  7       1     reserved = 0x00
  8       4     keyEpoch (uint32 BE)
  12      16    fileId
  28      16    versionId
  44      4     reserved2 = 0x00 (MUST be zero; nonzero = reject)

Records (repeated until end of bytes):
  u32 BE ciphertextLength   (must be >= 16; must be <= chunkMax + 16)
  24 bytes nonce            (random per record)
  ciphertext||tag           (ciphertextLength bytes)
```

Record types:

- Records `0 .. N-1`: data chunks. Plaintext length `1 .. chunkMax` (`chunkMax` default 4 MiB, protocol hard maximum 64 MiB). Empty files use one empty-plaintext data record (`ciphertextLength == 16`).
- Record `N` (mandatory, final): manifest record. Plaintext is UTF-8 canonical JSON (keys exactly as shown, no spaces):

```json
{"chunks":N,"size":totalPlaintextBytes,"v":1}
```

`chunkSize` is not required in the manifest; per-record plaintext lengths are implied by ciphertext lengths (`plaintextLen = ciphertextLength - 16`).

### Associated data (AAD)

All AAD inputs are the exact byte strings below; every record and the wrapped DEK/metadata use them. `epoch` = 4-byte BE `keyEpoch`.

```text
prefix   = "OCE1" || 0x01 || 0x01 || epoch || fileId || versionId
AAD_data(k)    = prefix || 0x00 || u32BE(k)
AAD_manifest   = prefix || 0x01
AAD_dek        = prefix || 0x02
AAD_metadata   = prefix || 0x03
```

Data record index `k` starts at 0 and increments by 1. The manifest follows the last data record with no gap.

## 5. Wrapped DEK and metadata blob

Stored as separate opaque fields (base64 in API JSON):

- `wrappedKey` = `nonce(24) || XChaCha20Poly1305(KEK, nonce, DEK, AAD_dek)`
- `metadataBlob` = `nonce(24) || XChaCha20Poly1305(MEK, nonce, metadataJSON, AAD_metadata)`

`metadataJSON` is UTF-8 canonical JSON with keys in lexicographic order among present keys:

```json
{ "description": "...", "mimeType": "application/pdf", "name": "report.pdf" }
```

`name` is required, `mimeType` and `description` optional.

**What is still visible in v1.** The plaintext name and MIME type are _not_ put in
the Telegram caption — the caption carries only `sha256:operationId` — but they
are still visible in two other places, and this document does not claim
otherwise:

- The server stores the plaintext name in `File.name` and the MIME type in
  `File.mimeType`, because the client sends the real name as the multipart
  filename and the server needs it to list and search.
- The Telegram document itself carries a filename attribute, taken from the
  upload's name.

So in v1 the content of a file is protected but its _name_ is not, from either
the API's database or the Telegram channel. Hiding it requires the opaque-name
and client-side-index design proposed in
[`architecture-decisions/0004-client-side-filename-index.md`](architecture-decisions/0004-client-side-filename-index.md);
it is not implemented.

## 6. Client algorithm requirements

Encrypt (per version):

1. Generate DEK, fileId (first version only), versionId, epoch 0.
2. Read source in chunks `<= chunkMax`; for chunk `k`: random 24-byte nonce; `ct = XChaCha20Poly1305(DEK, nonce, chunk, AAD_data(k))`; emit length, nonce, ct.
3. Emit manifest record with `AAD_manifest` and canonical JSON `{"chunks":N,"size":S,"v":1}`.
4. Wrap DEK under KEK; encrypt metadata under MEK.

Decrypt (whole object):

1. Parse header; reject bad magic/version/suite/flags/reserved; compare header `fileId`, `versionId`, `keyEpoch` to the caller's expected values (must match the wrappedKey/metadataBlob binding); reject mismatch.
2. Parse all records; require at least 2 records total: at least one data record (empty files use one empty-plaintext data record) followed by the manifest; reject trailing bytes; enforce length bounds.
3. After the first data record, each subsequent record is first attempted under `AAD_manifest`; a successful authentication identifies the manifest (which MUST be the final record). If that attempt fails with an authentication error, the record is attempted under `AAD_data(k)` for the next data index `k`. A record that authenticates under neither AAD is a hard failure. Parse the manifest; require `chunks == N` and `size == sum(plaintext lengths)`; then (and only then) return plaintext.
4. Any failure throws; callers MUST discard partial plaintext. No plaintext is returned for a stream that did not fully authenticate.

Resume: because every record uses an independent random 192-bit nonce, a resumed upload may re-encrypt from scratch under the same DEK with fresh nonces without nonce-reuse risk. Clients SHOULD reuse `fileId`/`versionId`/`DEK` only within a single unfinished version operation and MUST NOT append records to an existing finalized envelope.

## 7. Failure modes (normative error classes)

- `UnsupportedFormatError`: bad magic/version/suite/flags/reserved/lengths.
- `BindingError`: header ids/epoch do not match expected values.
- `AuthenticationError`: AEAD tag failure (wrong key, tampered bytes, reordered/duplicated records — every record's AAD includes its index, so reorder/duplication fails tag verification).
- `ManifestError`: missing manifest, manifest not last, chunk-count or size mismatch.
- `TrailingDataError`: bytes after manifest.

Every error is a distinct class in `packages/crypto`; messages MUST NOT include key material or plaintext.

## 8. Server contract (opaque object)

- Upload: server accepts `encryptionFormat: "OCE1"`, `wrappedKey`, `metadataBlob`, `keyEpoch` (all opaque to the server), stores the body bytes unchanged, and continues to compute a SHA-256 of the stored bytes for transport integrity only.
- Download: server returns the same opaque fields and the stored bytes.
- The server MUST NOT interpret envelope internals. Legacy plaintext files keep `encryptionFormat = null`.
- UI/API consumers MUST NOT display "encrypted" until the client has successfully decrypted and verified.

### v1 limitations (accepted for this provisional release)

- The plaintext filename is still sent to the server as the multipart filename and stored in `File.name` for list/search compatibility. Only file content and the metadata blob (`name`, `mimeType`, `description` inside `metadataBlob`) are encrypted client-side. Hiding the server-visible name requires a follow-up design for client-side listing and search and is not claimed by v1.
- Ciphertext size, timestamps, object references, and account mapping remain server-visible operational metadata.
- Resumable uploads re-encrypt from scratch under fresh random nonces; there is no persisted stream state.
- Web upload/download buffer the whole file in memory; large-file streaming in the Web client is future work. The SDK upload path buffers the envelope per operation as well.
- Recovery, device enrollment/revocation, sharing, and Android are not implemented.

## 9. Test vectors

`packages/crypto/test/vectors/` contains fixed URK/DEK/fileId/versionId/nonce inputs and the exact expected envelope bytes plus metadata/wrappedKey outputs, generated by the reference implementation with the pinned dependency versions and verified by independent decrypt-and-compare in tests. Any implementation of OCE1 (Web, CLI, Android) MUST reproduce these vectors byte-for-byte.

Known-answer vectors are test-only key material; they are not usable secrets.
